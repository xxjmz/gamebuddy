## Context

现有桌面端只有连接本地 Mod Bridge 的只读 WebSocket，`ws` 依赖目前仅用于客户端连接。全屏弹幕覆盖层已经能够显示带来源 metadata 的本地消息，但仓库没有公网中继、账户或玩家消息协议。

## Goals / Non-Goals

**Goals:**

- 以独立、可部署的 WebSocket relay 让自愿参与者按粗粒度游戏场景交换短弹幕。
- 默认不联网；开启后仅发送不可逆的场景匹配字段与匿名会话消息。
- 将服务不可用、节流、过滤和本地隐藏作为首期可靠性/安全边界。

**Non-Goals:**

- 不把 relay 做成游戏控制、战术协作、匹配排位、账号社交或聊天历史服务。
- 不从玩家消息调用 LLM、写入玩家记忆、补全游戏状态或生成战斗策略。

## Decisions

### 1. 使用独立 relay，而不是 Mod 或本地 LAN 广播

客户端通过环境配置的 WSS 地址加入 relay；relay 只维护内存中的短生命周期房间和会话。Mod 保持完全本地、只读且不感知玩家网络功能。LAN 广播无法可靠覆盖远程玩家；将 relay 混入主 Electron 进程会令所有桌面实例承担服务端暴露风险。

### 2. 使用粗粒度、不可逆的场景房间键

客户端从 Mod observation 生成规范化对象：协议/游戏版本、角色、act、floor、room 与按 ID/名称排序的在场敌人；对稳定 JSON 进行哈希并仅传 hash。这样可以把相似遭遇聚合，又不会上传完整状态。run seed、HP、手牌、牌组、遗物、建议和事件原文一律不进入对象。

### 3. 匿名、显式 opt-in 的临时会话

首次开启时客户端生成本地随机 session ID；默认关闭、关闭后断开。玩家消息不显示发送者身份。relay 仅维护连接期间的 session 与消息 TTL，不持久化消息。无身份会话避免首期账户、密码、昵称和身份数据处理，但不能提供跨设备封禁或信誉。

### 4. 消息协议和审核在 relay 侧执行

客户端可发送 `join`、`leave`、`message`，服务端可发送 `ready`、`message`、`rejected`、`error`。服务端验证 schema、匹配 room hash、限制消息长度/Unicode 控制字符和每会话频率，并使用与本地语料相同的策略/控制/广告过滤原则。客户端仍对收到的内容长度、来源和过期时间进行防御性校验，并可本地隐藏 `player` 来源。

### 5. 覆盖层不承担策略和持久聊天职责

玩家消息经主进程转为独立 `gamebuddy.danmaku.v1` 消息，`source=player`、`style=community`，并沿用 generation/过期机制。当前场景切换即离开旧 room 并清除旧消息，避免跨战斗泄漏。

## Risks / Trade-offs

- [匿名滥用与绕过过滤] → server-side 限流、短 TTL、文本过滤、会话级本地隐藏；正式上线前接入可配置审核和运营封禁。
- [粗粒度房间用户不足或误聚合] → 首期显示在线人数与“暂无同场玩家”；后续根据匿名指标调整 floor/敌人匹配粒度。
- [relay 宕机] → 连接退避和非阻塞状态，绝不影响 Mod 事实弹幕。
- [WebSocket 明文泄漏] → 生产环境 MUST 使用 WSS；本地开发才允许 `ws://127.0.0.1`。

## Migration Plan

1. 先以默认关闭的本地/测试 relay 验证协议和限流。
2. 部署 WSS relay 后在桌面端提供明确的 opt-in、隐私说明和状态指示。
3. 出现安全或稳定性问题时关闭 relay URL 或禁用开关即可回退；本地弹幕不受影响。

## Open Questions

- 首期 relay 的部署归属和域名尚未确定；实现使用环境变量配置地址，因此该问题不改变客户端协议或任务拆分。
